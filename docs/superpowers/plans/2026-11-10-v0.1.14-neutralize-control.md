# v0.1.14 收尾：恢复后中立化状态管理（保持/解除）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** 在插件端提供「保持中立化 / 解除中立化」两按钮与状态展示，让备份恢复闭环（备份→恢复→环境准备→安全隔离→决定站点是否接管生产）全部在插件设置页完成。

**Architecture:** 新增 `lib/neutralize.js`（纯函数：状态判定 SQL 构造 / 结果解析 / 解除 SQL 构造）+ Host 路由 `GET /neutralize-status`、`POST /neutralize-apply` + Client 设置页新增「中立化状态」卡片。所有远端操作走既有 `execRemote` 与 `guardDbName`，不新增 SSH/加密/凭证逻辑。解除操作前必须过 confirmToken 闸门（复用 `tokenStore`），因为它是破坏性、不可逆的生产数据变更。

**Tech Stack:** Node ESM、`node:test`、PostgreSQL `psql -AtF|`、现有 `execRemote` / `createService` / `handleUiRequest` / `settings.section`。

**Spec:** 本会话用户裁决（2026-11-10）：「两按钮 + 状态展示（推荐）」；完整对比报告确认 neutralize 现状。

## Global Constraints

- **版本仍 `0.1.14`**（收尾修改，不新开版本）；构建后重新记录 SHA256。
- **不改变** R10 加解密、Credentials、SSH 指纹、confirmToken 机制、恢复事务/回滚、备份格式。
- **不改变** 恢复时的 `neutralize` 选项语义（它仍是 `odoo db load -n` 的参数，防误发邮件）。本次是**恢复之后**的事后状态管理，两者独立。
- **安全边界（关键，来自真机实证）**：`payment/data/neutralize.sql` 只做 `UPDATE payment_provider SET state='disabled' WHERE state NOT IN ('test','disabled')`，**不记录**哪些原本 enabled。源机实测 enabled = id 25 `alipay`、id 110 `airwallex`；恢复机数据本身无法推知。⇒ **解除中立化绝不猜支付提供商**，必须用户提供明确名单，或默认只解除 base neutralize 可还原项、支付保持 disabled 并明确告知。
- **不可逆项必须显式告知**：SMTP 凭据被 `smtp_user=NULL` / `smtp_pass=NULL` 清空，无法从恢复库还原（源机是 `cs@toogel.cn`，但凭据来自 conf/env，插件不得跨机读取生产库）。解除后需人工在 Odoo 后台重填。
- **不擅自改 Compose / conf 挂载 / web.base.url / website.domain**（用户已裁决这些是独立部署事项）。
- **目标库名必须明确**：所有 SQL 只对 `guardDbName(instance.dbName)` 指向的**目标库**执行，绝不跨库、绝不碰生产库。
- **不记录任何密钥/凭据明文**到日志、状态、UI。
- 全部编码按 TDD（RED→GREEN）；真机验证用临时库或用户明确授权的目标库。

### Task 1: `lib/neutralize.js` — 状态判定与解除 SQL（纯函数）

**Interfaces:**
- Consumes: `guardDbName` 由调用方保证已校验；无外部 IO。
- Produces:
  - `export const NEUTRALIZE_STATUS_SQL`
  - `export function buildStatusScript()` → shell 脚本字符串（stdin: PG/PG_SUPER/DB）
  - `export function parseStatus(stdout)` → `{ ok, neutralized, cronActive, cronTotal, mailServers, paymentEnabled, paymentDisabled, webhookNeutralized, flag, reason? }`
  - `export const APPLY_NEUTRALIZE_SQL` / `export function buildApplyScript({ enablePaymentCodes })` → shell 脚本
  - `export function parseApplyResult(stdout)` → `{ ok, applied, cronEnabled, paymentEnabled, mailPlaceholderRemoved, flagRemoved, restartRequired, warnings, reason? }`

**判定依据（真机实证 + Odoo 官方 neutralize.sql）：**
- flag：`database.is_neutralized` = true
- cron：`ir_cron.active`（源机 36 enabled / 7 disabled；目标机 1 enabled / 42 disabled）
- 邮件：`ir_mail_server` 里 `smtp_host='invalid'` 的占位行 + 原行被 `active=false, smtp_user=NULL`
- 支付：`payment_provider.state`（payment 模块 neutralize 把非 test/disabled 全置 disabled）
- webhook：`ir_act_server.webhook_url='neutralization - disable webhook'`
- `neutralized = flag===true || cronActive===0 || 占位邮件服务器存在`（任一即为中立化）

**解除 SQL 必须做（base neutralize 可还原项）：**
1. `DELETE FROM ir_config_parameter WHERE key='database.is_neutralized'`
2. `UPDATE ir_cron SET active=true`（含源机 36 个；不启用 autovacuum 例外——那是 Odoo 自己保留的，源机也是 enabled 计）
3. `DELETE FROM ir_mail_server WHERE smtp_host='invalid' AND name='neutralization - disable emails'`
4. `UPDATE ir_mail_server SET active=true WHERE smtp_host<>'invalid'`（**凭据仍为 NULL，必须 warning 提示人工重填**）
5. `UPDATE ir_act_server SET webhook_url=NULL WHERE webhook_url='neutralization - disable webhook'`
6. `DELETE FROM mail_mail WHERE state IN ('exception','outgoing')`（**先清未发邮件**，否则 cron 一开就批量重发；源机也有 22 条 exception，属历史遗留，不动 sent）
7. 支付：仅当调用方显式传 `enablePaymentCodes`（字符串数组）时 `UPDATE payment_provider SET state='enabled' WHERE code = ANY(...)`；否则**全部保持 disabled** 并 warning。绝不猜。
8. `restartRequired=true`（Odoo 缓存 + max_cron_threads 需重启；插件不改 conf）

### Task 2: `lib/service.js` — 状态查询与解除操作

**Interfaces:**
- Consumes: `d.discover(server)` → `instance.dbName`；`requireTrusted(name)`；`execRemote`；`guardDbName`
- Produces:
  - `service.neutralizeStatus(name)` → `parseStatus` 结果 + `{ dbName }`
  - `service.applyNeutralize(name, action, opts = {})` → `parseApplyResult` 结果；`action` 必须是 `'keep'` 或 `'release'`；`'keep'` 直接返回 `{ ok:true, applied:false, action:'keep', reason:'保持中立化，未改动目标库' }`（不执行任何 SQL）
- `release` 前：`guardDbName(instance.dbName)` 校验；`opts.enablePaymentCodes` 透传（默认空）
- 所有远端操作走 `execRemote(server, script, { stdin:[pgContainer, pgSuperUser, db].join('\n') })`

### Task 3: `index.js` — Host 路由（含 confirmToken 闸门）

**Interfaces:**
- Consumes: `service.*`、`tokenStore`、`unwrapVolatile(config.servers)`
- Produces:
  - `GET/POST /neutralize-status`：`{ ok:true, ...status, dbName }`
  - `POST /neutralize-apply`：
    - `body.action` 必须 `'keep' | 'release'`
    - `body.server` 必须存在
    - **`release` 必须带 `body.confirmToken`**，且 `tokenStore.verify(confirmToken, { server, action:'release', dbName })`（新绑定键 `action`/`dbName`，一次性 + 5 分钟）
    - `keep` **不需要** token（无破坏性）
    - 调用 `service.applyNeutralize`，返回结果
  - `POST /neutralize-precheck`：为 release 生成 confirmToken（绑定 server + action + dbName），返回 `{ ok:true, confirmToken, expiresInSeconds:300, warnings: [...] }`
    - `warnings` 固定含：① SMTP 凭据已被清空、解除后需人工重填；② 未发邮件将被清除；③ 支付提供商默认保持 disabled（除非显式传 enablePaymentCodes）；④ 解除后需重启 Odoo 容器且 cron 会立即开始运行；⑤ **该操作不可逆，请确认目标环境确需接管生产**。

**已知风险（写进实现注释与 UI 文案）：**
1. 支付 enabled 无法从恢复库推知 → 默认保持禁用，用户显式给 code 才启用。
2. SMTP 凭据被清空且不可逆 → 解除后必须人工重填。
3. `UPDATE ir_cron SET active=true` 会启用**全部** cron（源机 36 enabled / 7 disabled，即 7 个原本 disabled 的也会被启用）→ 更安全的做法是**只启用 neutralize 停用的那些**，但 Odoo neutralize 没留标记。折中：解除前先查询当前 disabled 的 cron 名单并回报，让 UI 明确告出「将启用 N 个定时任务」，由用户确认；不擅自只挑一部分。本方案的 `UPDATE ir_cron SET active=true WHERE active=false` + status 里回报 `cronDisabled` 数，UI 二次确认里显示这个数字。
4. `max_cron_threads` 在 conf 里（目标机未挂载），插件不改 conf；解除后即使 cron 记录 active=true，若 conf 仍是 0 也不会跑 → UI 明确提示「需确认 max_cron_threads≥1 并重启容器」。
